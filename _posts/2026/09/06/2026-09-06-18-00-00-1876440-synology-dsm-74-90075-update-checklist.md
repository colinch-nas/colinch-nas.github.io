DSM 7.4-90075는 그냥 눌러서 올릴 업데이트가 아니다. Synology 공식 릴리스 노트 기준으로 설치 뒤 이전 DSM으로 **다운그레이드할 수 없고**, 설치 과정에서 NAS가 재부팅된다. 나는 DS923+에서 Docker와 Jellyfin을 돌리고 있어서, 패키지 백업을 확인한 뒤 수동 업데이트하는 쪽을 택했다. 이 글은 2026년 9월 6일 기준으로 DSM 7.4-90075를 올리기 전 확인할 항목을 정리한 것이다.

## 업데이트 전에 확인할 조건

DSM 7.4는 2026년 6월 16일 공개됐고, 90075는 보안 취약점 수정이 포함된 유지보수 버전이다. 다만 모든 모델이 같은 방식으로 노출되는 것은 아니다. 일부 구형 모델은 자동 알림이 오지 않고, DSM 7.4가 마지막 업그레이드 버전이 된다.

| 점검 항목 | 확인 기준 | 문제가 있으면 |
|---|---|---|
| 모델 지원 | 제어판 → 정보 센터에서 모델명 확인 | Synology Download Center에서 모델별 `.pat` 확인 |
| 현재 DSM | 7.3 계열인지 확인 | 현재 버전과 모델용 릴리스 노트 대조 |
| 다운그레이드 | 7.4-90075 설치 후 불가 | 테스트 NAS가 아니면 복구 계획 수립 |
| 재부팅 | 설치 중 서비스 중단 | Jellyfin·Docker 사용 시간 피하기 |
| 백업 | Hyper Backup 작업 성공 여부 | 파일 복사와 설정 백업을 각각 확인 |

이 그림에서 봐야 할 부분은 NAS 자체보다 왼쪽의 업데이트 확인 화면과 오른쪽의 별도 백업 디스크다. DSM 업데이트 파일이 정상이어도, 업데이트 실패에 대비한 복구 수단이 없으면 안전한 작업이 아니다.

## 1. 설정과 컨테이너 상태를 저장한다

Hyper Backup으로 `docker`, 공유 폴더, DSM 구성 백업을 각각 확인했다. Docker Compose 파일과 `.env`는 백업 작업에 포함됐는지 별도로 열어보는 게 좋다. 데이터만 있고 컨테이너 설정이 없으면 복구할 때 포트와 볼륨 매핑을 다시 만들어야 한다.

Docker를 사용한다면 업데이트 전 실행 중인 컨테이너 목록도 기록한다. 이 명령은 삭제가 아니라 현재 상태를 저장하기 위한 확인용이다.

```bash
sudo docker ps --format "table {{.Names}}\t{{.Image}}\t{{.Status}}" > /volume1/backup/docker-before-dsm.txt
```

Hyper Backup의 작업 기록은 `성공`이어야 한다. 예약만 걸려 있고 마지막 실행이 실패한 상태라면 DSM 업데이트를 미루는 편이 낫다. 스냅샷은 백업이 아니므로, Btrfs 스냅샷만 믿고 진행하지 않았다.

## 2. 패키지와 외부 접속을 잠시 정리한다

패키지 센터에서 Docker, Jellyfin, Synology Photos처럼 사용 중인 패키지에 업데이트 대기 항목이 있는지 확인한다. DSM과 패키지를 같은 날 한꺼번에 올리면 문제가 생겼을 때 원인을 찾기 어렵다. 이번 작업에서는 DSM만 올리고, 재부팅 뒤 패키지별 정상 여부를 확인한 뒤 패키지 업데이트를 진행한다.

외부 접속을 열어둔 NAS라면 역방향 프록시(외부 도메인 요청을 내부 서비스로 전달하는 중계 서버)와 DDNS도 점검한다. 업데이트 직후 인증서 갱신까지 겹치면 장애처럼 보일 수 있다. 작업 시간에는 관리자 화면을 내부 IP로 열고, 포트 포워딩을 임시로 추가하지 않았다.

## 3. DSM 7.4-90075 수동 업데이트

자동 업데이트 알림이 보이면 모델과 버전을 다시 확인한다. 알림이 없거나 구형 모델이라면 Synology Download Center에서 모델에 맞는 DSM 7.4-90075 `.pat` 파일을 받아 수동으로 진행한다.

경로는 `제어판 → 업데이트 및 복원 → DSM 업데이트 → 수동 DSM 업데이트`다. 파일을 선택하고 호환성 경고를 읽은 뒤 설치를 시작한다. 설치 중 전원을 끄거나 공유기 설정을 바꾸지 않는다. DS923+에서 설치 후 재부팅과 서비스 복구까지 약 10분이 걸렸지만, 디스크 검사나 패키지 상태에 따라 더 길어질 수 있다.

## 재부팅 뒤 확인할 것

```text
제어판 → 정보 센터: DSM 7.4-90075
저장소 관리자: 풀·볼륨 정상, 드라이브 경고 없음
패키지 센터: Docker/Jellyfin 실행 상태
파일 스테이션: SMB 읽기·쓰기
로그 센터: 부팅 직후 오류 반복 여부
```

특히 Docker 컨테이너가 `exited`로 남는지 확인한다. 컨테이너가 자동 시작되지 않으면 Compose 스택을 무작정 재생성하지 말고, 볼륨 경로와 권한부터 비교한다. SMB는 PC 한 대에서 작은 파일을 만들고 삭제하는 정도로도 빠르게 확인할 수 있다.

## 짧은 요점 정리

DSM 7.4-90075는 보안 수정만 보고 바로 설치하기보다, 다운그레이드 불가라는 조건을 기준으로 판단해야 한다. 모델별 지원 여부를 확인하고, Hyper Backup 성공 기록과 Docker 설정 파일을 확보한 뒤 작업 시간을 잡는다. 업데이트 후에는 버전 표시보다 저장소·패키지·SMB·로그를 실제로 확인해야 완료다.
