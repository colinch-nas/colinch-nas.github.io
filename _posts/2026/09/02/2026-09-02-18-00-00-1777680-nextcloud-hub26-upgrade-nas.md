Nextcloud Hub 26 Spring을 NAS에 적용할 때는 컨테이너 이미지만 바꾸면 끝난다고 생각하면 안 된다. 내가 확인한 기준으로는 데이터베이스와 `config` 백업을 만들고, 현재 앱 호환성을 확인한 뒤 한 단계씩 올리는 편이 안전하다. 특히 Docker Compose에서 `latest`를 그대로 쓰면 재시작 한 번에 예상하지 못한 메이저 업데이트가 들어올 수 있다.

## 이번 업데이트에서 확인할 환경

Nextcloud 공식 발표에 따르면 Hub 26 Spring은 Euro-Office 선택지, 가벼워진 UI, Governance 기능을 포함한 릴리스다. Hub 버전 이름과 Docker 이미지 태그 숫자는 1:1로 대응하지 않으므로, NAS에 설치된 앱은 서버 코어와 별개로 호환 여부를 확인해야 한다.

| 항목 | 확인 기준 |
|---|---|
| NAS | Synology DS923+ 또는 x86-64 NAS |
| 실행 방식 | Docker Compose |
| 데이터베이스 | MariaDB 10.11 |
| 업데이트 전 | Nextcloud 관리자 화면의 앱 업데이트 완료 |
| 백업 | DB 덤프 1개 + `config`와 data 스냅샷 |

기존 글에서 Nextcloud 30을 처음 설치했다면, 이번 작업은 새 컨테이너를 만드는 과정이 아니라 기존 볼륨을 유지한 채 이미지 태그를 변경하는 작업이다. 볼륨 경로를 잘못 쓰면 로그인 정보는 남아도 파일 목록이 비어 보일 수 있다.

## 업그레이드 전 백업

웹 화면의 백업 버튼만 믿지 않고 MariaDB 덤프를 별도로 저장한다. 아래 경로는 예시이며, 실제 Compose 파일의 DB 컨테이너 이름을 확인해서 바꿔야 한다.

```bash
cd /volume1/docker/nextcloud
mkdir -p backup/2026-09-02
docker exec nextcloud-db mariadb-dump -u root -p nextcloud \
  > backup/2026-09-02/nextcloud.sql
cp html/config/config.php backup/2026-09-02/config.php
```

덤프 파일이 0바이트인지 꼭 확인한다. 암호를 잘못 입력해도 리다이렉션 때문에 빈 파일이 미리 만들어져 성공한 것처럼 보이는 삽질을 한 적이 있다.

```bash
du -h backup/2026-09-02/nextcloud.sql
docker exec nextcloud php occ maintenance:mode --on
```

가능하면 NAS 스냅샷으로 `html`과 data 디렉터리도 함께 보존한다. RAID는 디스크 고장 대비용이지, 잘못된 업그레이드 복구용 백업이 아니다.

## Docker 이미지 태그를 고정해 업데이트

Compose 파일의 `image`를 공식 Docker 이미지의 안정 채널로 바꾼다. Hub 26 Spring의 `26`을 그대로 Docker 태그로 쓰면 안 된다. 실제 서버 태그는 [Nextcloud Docker 이미지](https://hub.docker.com/_/nextcloud)의 현재 지원 범위를 확인한 뒤 고정한다.

```yaml
services:
  nextcloud:
    image: nextcloud:stable-apache
    container_name: nextcloud
    restart: unless-stopped
```

`latest` 대신 메이저 태그를 쓰면 자동 재시작 후 버전이 바뀌는 일을 줄일 수 있다. Compose 파일을 저장한 뒤 컨테이너를 다시 만든다.

```bash
docker compose pull nextcloud
docker compose up -d nextcloud
docker logs -f --tail=100 nextcloud
```

로그에 데이터베이스 마이그레이션 완료가 보일 때까지 브라우저를 새로고침하지 않는다. 업데이트 직후 502가 나오면 바로 롤백하기보다 2~5분 정도 로그를 확인한다. 테이블 변경 중 컨테이너를 강제 종료하면 복구가 더 어려워진다.

## occ 점검과 외부 접속 확인

컨테이너가 정상 기동하면 유지보수 모드를 끄고 누락된 인덱스와 파일 스캔 상태를 확인한다.

```bash
docker exec nextcloud php occ upgrade
docker exec nextcloud php occ maintenance:repair
docker exec nextcloud php occ maintenance:mode --off
docker exec nextcloud php occ db:add-missing-indices
```

그 다음 내부 IP와 외부 도메인에서 각각 로그인한다. Reverse Proxy(외부 도메인 요청을 내부 서버로 전달하는 중계 서버)를 쓰고 있다면 HTTPS 리다이렉트, 업로드 용량, WebSocket 오류를 따로 확인한다. `Access through untrusted domain`이 나오면 `config.php`의 `trusted_domains`에 현재 도메인이 있는지 확인한다.

| 확인 항목 | 정상 기준 |
|---|---|
| 기존 사용자·공유 링크 | 이전 링크가 열림 |
| 모바일 자동 업로드 | 새 사진 1장 업로드 성공 |
| MariaDB | 컨테이너 재시작 후에도 데이터 유지 |
| 외부 접속 | HTTPS와 인증서 경고 없음 |
| 관리자 화면 | 보안 경고와 앱 호환성 경고 확인 |

## 여기서 멈춰야 하는 경우

앱 업데이트 화면에 호환 불가 표시가 있거나, DB 덤프를 복원 테스트하지 못했다면 메이저 업그레이드를 미룬다. 사진과 문서가 NAS 한 곳에만 있다면 업데이트보다 백업 복사본을 다른 장치에 만드는 일이 우선이다. Hub 26의 새 기능이 필요한 상황이어도 자동화된 백업 없는 운영은 감당할 수 있는 장애 범위를 넘는다.

짧게 정리하면 `백업 → 앱 호환성 확인 → 이미지 태그 고정 → 로그 확인 → occ 점검 → 내부·외부 접속 테스트` 순서다. 참고한 릴리스 내용은 [Nextcloud Hub 26 Spring 공식 발표](https://nextcloud.com/blog/press_releases/nextcloud-hub-26-spring-delivers-new-office-experience-lighter-ui-and-and-a-new-governance-tool/)와 [Nextcloud 관리자 문서](https://docs.nextcloud.com/server/latest/admin_manual/)에서 확인할 수 있다.
